# 检索触发机制：开源 AI 小说项目对比与 choice_novel 落地报告

> 本文对比 13 个开源 AI 小说项目与 choice_novel 自身对「**生成时是否需要网络搜索 / 设定召回（RAG），以及按什么触发**」的处理，评估 choice_novel 新增「一次 LLM 判定检索画像 + 分层检索」在开源生态中的位置与差距。

---

## 这份报告是干嘛的

简单说，这篇文档是在回答两个问题：
1. **别人家的 AI 小说工具，是怎么决定"写这一段的时候，要不要上网查点资料、要不要回头翻翻前面写过的设定"的？** 我们把这些开源项目一个个扒开来看了一圈。
2. **我们 choice_novel 自己是怎么做的，站在这一圈开源项目里属于什么水平，哪里比人家强、哪里还差、下一步能抄谁家作业。**

下文会遍历一圈开源项目，然后给出横向对比，最后落在我们自己该怎么落地。

---

## 1. 背景：要解决的问题

写小说的时候，AI 最容易翻的两类车：
- **事实错**（历史、军事、医疗、法律这类题材，全靠编，细节对不上）；
- **前后矛盾**（角色、埋伏笔、时间线、世界观设定前后打架）。

上网搜能解决前者（查真实资料），回头翻设定能解决后者（记着之前定下的东西）。但"要不要搜、搜什么"不能一刀切，得看四件事来判断：

| 判断维度 | 怎么判断 | 典型的该搜/该查场景 |
|---|---|---|
| 真实事实密度 | 是不是涉及真实的历史、地理、人物、事件、科技 | 历史、传记、地域纪实 |
| 专业深度 | 是不是涉及专业的流程、术语、规矩 | 医学、法律、军事、金融、采矿 |
| 时效性 | 是不是依赖"当下正在变的现实" | 最新政策、在售产品、时事、热搜 |
| 设定连续性 | 是不是长篇、系列、架空设定，需要前后对得上 | 所有长篇、群像、埋伏笔的书 |

**这篇文档盯的焦点**：这一堆开源项目里，谁做了上网搜、谁做了翻设定、谁做了"按维度/按类型决定什么时候搜、搜什么"——以及 choice_novel 自己的实现到底站在哪。

## 2. choice_novel 自身实现（本次新增）

### 2.1 大致的路子
开一本书的时候，先用 LLM 一次性判断上面那四个维度 → 得出一个"检索画像"（这份书大概需要什么资料、要不要联网）→ 按这个画像，把该预取的资料在开书时一批并行拉回来 → 正文写作的时候，只有"时效性高"的环节才轻量联网一下。旧的"从文本里抠英文单词再去联网"的笨办法，直接删掉。

| 步骤 | 干什么 | 关键文件:位置 |
|---|---|---|
| 开书·第1步 | `ProfileDeterminer.determine()` 用一次 LLM 判断四个维度 + 提炼中文主题 | `backend/app/services/retrieval.py`；`story_service.py:187-197` |
| 开书·第2步 | `prefetch()` 按画像里的主题**并行预取**，塞进 `story.grounding` 当正文的依据 | `story_service.py:210` |
| 开书·第1步 | `resolve()` 从知识库里把相关实体调出来 | `story_service.py:187` |
| 正文·每一段 | `_ground_decision()`：离线知识库捞相关设定**每一段都跑**；**只有** `timeliness=high` 且确实要联网、且配了联网开关时才**上网** | `story_service.py:362-389` |

### 2.2 什么时候触发（改造完以后）
- **上网搜的时机**：不再靠文本正则去猜，而是看检索画像。开书时预取一次；正文里只在"时效性高"的那类段落轻搜一次（超时设得短、失败了也不报错、静默默认过）。
- **翻设定的时机**：还是按"提到某个实体名字"来——文本里真的写到了某个真实存在的名字（比如刘强东、京东……）才把相关设定喂进去；纯架空的情节，一点不喂。
- **没配 key 就降级**：`WebSearch.enabled` 取决于你有没有配 `search_api_key`；没配 → 开书时预取跳空、正文也不联网，退回到只翻设定，行为和旧系统一模一样。

### 2.3 检索画像长什么样（存在 `story.retrieval_profile`）
```jsonc
{
  "real_world": "high",
  "profession": {"level": "high", "domains": ["采掘", "安全规程"]},
  "timeliness": "low",
  "continuity": "high",
  "topics": [{"label": "煤矿井工开采主要流程", "kind": "professional"}],
  "require_web": true
}
```

## 3. 开源项目全景（13 个）

### 3.1 denova（Go 写的 / 内置 Agents·Skills·SubAgent）
- **上网搜** ✅ 有 `web_search` 和 `web_fetch` 两个搜索工具，优先用 SearXNG，DuckDuckGo/Bing 并发兜底；由 LLM 在写作过程中**自己决定**要不要调用哪个搜索工具。
- **翻设定（AI 语义匹配）** ❌ 没有语义向量那套；资料库用的是**关键词/倒排索引**去捞，另外有 `resident/auto/manual`（常驻/自动/手动）三种模式。
- **翻设定** ✅ `resident` 模式会把资料常驻、全量塞进提示词，另外 `auto/manual` 是当工具的按需检索。
- **按类型区分对待** ❌ 全球统一一套，题材（genre）只拿来预设交互事件用。
- **前后一致性核查** ❌ 基本没有正文一致性引擎。
- **一句话定位**：上网搜和资料库它都有，但全靠 agent 自己选、不按类型分流，正文一致性弱。

### 3.2 kimi-writer（Python 写的 / kimi-k2-thinking 自主 agent）
- **上网搜** ❌ 没有（唯一的 HTTP 请求是算 token 的接口）。
- **AI 语义匹配** ❌ 没有。
- **翻设定** 只在上下文太长超限时，把早先的对话**压缩成一段摘要**（从全量变成摘要），不是正经的检索。
- **按类型区分** ❌ **一致性核查** ❌。
- **一句话定位**：纯提示词写法的写作 agent，上网、翻设定、核查全都没有，是最原始的青涩样子。

### 3.3 storyforge（TS/Vue 写的）
- **上网搜** ❌ 没有。
- **AI 语义匹配** ✅ 很完整：有嵌入向量适配器 + `retrievalChunks` 向量 + `canon-provider` 按字段定策略；不过主检索其实靠关键词 + 摘要，向量主要是给语义评审用的。
- **翻设定** ✅ 多层检索塞入：把章节切块、做摘要、**直接前文**、长期档案（`consistency-dossier`）、时间线、知识台账都作为来源；`must-read`·`pinned` 的资料常驻。
- **按类型区分** ⚠️ 按**任务类型 task kind**（写正文/写大纲/写人物…）分配上下文预算，不是按小说题材分。
- **一致性核查** ✅ **最强**：有 `prose-semantic-review`（能查世界设定跟正文冲突、前文矛盾、人物视角泄露不该知道的信息、剧透、偏离大纲、人物动机断裂，还分 blocking 直接卡住 / warning 只提醒）+ `consistency-agent`（管已拿道具、知识台账、生命周期边界）。
- **一句话定位**：一点不上网，但翻设定和一致性核查做得最深。

### 3.4 OpenFic（Python/FastAPI 写的）
- **上网搜** ✅ 接了一堆 provider（brave/serper/searxng/tavily/ddgs/exa/jina/perplexity/zhipu 共 9 个），LLM 在"思考-行动-观察"这种循环里按需调用，默认是关着的。
- **翻设定（AI 语义匹配）** ✅ 章节向量检索（嵌入向量 + 可选再排序 + 混合 RRF），有"新鲜度"开关把关。
- **翻设定** 主要是固定窗口的章节上下文（近 9 章原文 + 远期摘要）；世界书是关键词子串检索。
- **按类型区分** ❌ **一致性核查** ⚠️ 那个 web_search 自称是用于事实核查，但靠 agent 自觉去调 + auditor/reviewer 这种子 agent，没有自动的后处理。
- **一句话定位**：上网搜和向量检索都有，agent 自主触发，没有类型分流、也没有自动事实核查。

### 3.5 AI-Novel-Writing-Assistant（也叫 Biz Novel Studio）
- **上网搜** ❌ 写作过程中不做；它只有一个独立的市场榜单爬虫（番茄/起点/晋江）用来做市场雷达。
- **翻设定（AI 语义匹配）** ✅ **最强**：Qdrant 向量 + 关键词 + RRF + reranker，chunk 有 facet（比如 genreTags 题材标签）；每章按**"任务感知"的查询**（mission/目标/角色）自动召回相关资料。
- **翻设定** ✅ 每章"使命感知"检索 + `completedMilestones`（已完成的里程碑这种不可逆事实账本）注入。
- **按类型区分** ⚠️ 检索全局统一一套；genreTags 只当作 facet（在看书分析那个场景用）。
- **一致性核查** ✅ 有章节评审 + AuditService（审计服务）+ 时间线一致性检查工具。
- **一句话定位**：写作中不上网，Qdrant 的混合式资料匹配做得最强，靠任务感知做召回 + 评审。

### 3.6 AI-Novel-Writer（electron/TS 写的桌面程序）
- **上网搜** ❌ 没有。
- **翻设定（AI 语义匹配）** ✅ 本地向量库（l2）+ 全文检索；`search_knowledge` 暴露给 agent 用。
- **翻设定** ✅ 分 L0(L500)–L1(编辑器感知)–L2(agent 按需 read_*/search_knowledge) 三级注入。
- **按类型区分** ❌ **一致性核查** ⚠️ 只在生成前做个 `continuity-preflight` 规则校验。
- **一句话定位**：不上网，全靠本地向量知识库做语义检索，agent 按需去取。

### 3.7 NovelClaw（Python/FastAPI 写的）
- **上网搜** ❌ 没有。
- **翻设定（AI 语义匹配）** ✅ ChromaDB 双库：一个记忆系统（把文本/大纲/人物/世界观/情节点/事实卡都向量化）+ 一个静态知识库（导入的资料按 genre 过滤）。
- **翻设定** ✅ 混着来：无条件注入滚动摘要/最近事实 + 向量和词法检索去补人物/大纲/世界观/埋伏笔。
- **按类型区分** ⚠️ genre 只拿来当知识库的过滤条件，检索方式还是同一套。
- **一致性核查** ✅ 有 `check_character/plot/world` + `comprehensive_check`（用 LLM 对着检索出来的记忆做综合评测）。
- **一句话定位**：纯翻设定的路子，双库 + 专门的一致性检查器，一点不上网。

### 3.8 oh-story-claudecode（Claude 技能套件）
- **上网搜** ✅ 做成**按需的"调查员"agent**：碰到需要查证的外部事实（历史制度/地理/职业/风俗）就暂停写作，拉一个 `story-researcher` 用 CDP 去搜 Google/Bing + WebSearch/webReader，还带来源存档；另外 `story-long-scan` 用浏览器爬虫扫榜做市场研究。
- **翻设定（AI 语义匹配）** ❌ 没有数值向量；知识体系是静态 markdown + "按需加载"。
- **翻设定** ✅ 文件式的**"预算"式召回**：每章只读"不读就会写错"的角色状态/待收伏笔/相关设定；还分跨书/文风/情绪分项召回；有 30+ 细分的题材卡。
- **按类型区分** ⚠️ 在内容层靠题材卡/数据源选择（30+ 细分映射），不是自动路由。
- **一致性核查** ✅ story-review + story-deslop。
- **一句话定位**：把上网搜做成"需要查证才搜"的独立调查员 agent + 文件式预算召回，它的触发设计最接近"按需查证"这个思路。

### 3.9 chinese-novelist-skill（中文小说技能包）
- **上网搜** ❌ **语义匹配** ❌。
- **翻设定** 一上来全量塞大纲/人物档案/文风基准/上一章结尾，外加一个"设定词典"专门维护专有名词的一致性。
- **按类型区分** ❌ 第 1 阶段问询定位，之后生成统一一套。
- **一致性核查** ⚠️ 第 4 阶段做字数/质量自动校验，不合格自动重写（最多 3 轮）。
- **一句话定位**：上网和语义匹配都没有，纯提示词全量塞 + 设定词典。

### 3.10 neuro-book（Bun/TS 写的）
- **上网搜** ❌ 没有。
- **翻设定（AI 语义匹配）** ✅ 自研 nb-memory：**bi-temporal 双时间轴**（一条按"摄入顺序 tick"，一条按"故事内时间 instant"），embedding + BM25 RRF + 启发式/LLM 查询规划器，用"as-of 时间点查询"**防止未来信息倒灌**（基准测试里时间泄漏率 0%）。
- **翻设定** ✅ 是检索式记忆引擎（目前还是个独立框架，还没观察到接入生成提示词的调用链）。
- **按类型区分** ❌ **一致性核查** ⚠️ 引擎本身的目标就是防时间倒灌；`llmlint` 只做风格/"AI 味"检测（不是一致性）。
- **一句话定位**：自研双时间轴记忆 + 检索引擎，专攻长文连贯性和时间线防泄漏，但还没接进写作链路。

### 3.11 terminal-velocity
- 这是一本由 10 个 AI agent（KinOS v6）各自独立写成的 10 万字完稿**成书产物**，不是可复用的工具；它的 `ResearcherAgent` 曾经联网做过设定验证，属于成书那一侧的一次性行为。

### 3.12 motion-ref-skill / ui-craft
- 前端设计技能，跟小说生成无关，凑数的。

## 5. 按四个维度看：谁最强、谁缺席

- **真实事实 → 上网搜**：`oh-story` 最接近（遇到要查证的事实就停笔、联网查证、还带来源存档）；`OpenFic`（9 个 provider）/`denova` 有搜索工具，但没有"该查才查"的触发机制。**没有任何一个项目会去校验网络返回的东西是不是真、是不是权威**。
- **专业深度 → 权威资料**：只有 `NovelClaw` 的静态知识库支持导入专业语料并按 genre 过滤；其余都没有"教材/论文/手册"这一层专业资料。
- **时效性 → 实时搜索**：`OpenFic`/`oh-story`/`denova` 能拿到实时信息，但**没有判断"这书要不要时效性"的触发逻辑**；`choice_novel` 是唯一把"时效性"写进判定、并且只对这一维度开放正文联网的。
- **设定连续性 → 翻设定**：`storyforge`、`Biz`、`NovelClaw`、`neuro-book` 做得最深；尤其 `neuro-book` 的**时间线防未来信息泄露**和 `storyforge` 的**伏笔/持有物/认知边界一致性 agent**，直接打在了长篇连贯性这个痛点上。

## 6. choice_novel 与开源的差距与可借鉴

**独有优势**：choice_novel 是**唯一把"要不要搜、搜什么"做成开书一次、四维度结构化判定的项目**。别的项目要么"agent 自己凭感觉决定调不调工具"（denova/OpenFic），要么"关了网不搜"（storyforge/Biz/NovelClaw/Writer/neuro-book），要么"只靠题材卡在内容层切换"（oh-story）。没有任何一家是在生产链路里先做一次画像判定、再根据画像去路由搜索和检索的。

**三大差距（能落地改进的）**：
1. **翻前文/设定还是全量塞**：`facts.py` 把角色/伏笔/规则/关系整份塞进提示词，长篇越写越大。而 `storyforge`/`Biz` 已经是检索式了、`neuro-book` 还能防时间泄漏。→ 下一步可以把 facts 改成按长度/相关性裁剪的检索式注入。
2. **一致性核查只有 LLM 自检，没有外部交叉**：`storyforge` 的语义评审代码集（world-rule-conflict、pov-knowledge-leak…）和 `NovelClaw` 的多维度一致性检查器更硬。→ 可以把 consistency 从"过没过/有啥问题"升级成"按问题分类写清楚"的评审。
3. **网络数据源单一（只有 Tavily）**：`OpenFic` 接了 9 个 provider。→ 如果需要，可以做成可扩展的 provider。

**一句话结论**：choice_novel 已经站在了开源生态的空当上——"按维度去决策检索"目前没人做全；而"翻设定"和"生成后的一致性核查"是开源强项的领域，可以作为下一步对标的方向。
