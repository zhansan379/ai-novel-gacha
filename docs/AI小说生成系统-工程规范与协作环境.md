## 1. 技术栈与目录结构（唯一事实源）

### 1.1 栈（与设计文档一致）

"技术栈"就是"咱们用什么工具、什么语言来盖这个房子"。清单如下：

- **后端**（服务端，负责跑逻辑、处理数据）：Python 3.12 + FastAPI + LangGraph。其中 Python 是编程语言；FastAPI 是"接收请求、返回结果"的框架；LangGraph 是编排 AI 大模型对话流程的库。包管理用 `uv`（装依赖包的工具）；数据读写用 SQLModel/SQLAlchemy（操作数据库的接口）；数据校验用 Pydantic v2（检查传进来的数据格式对不对）。
- **前端**（用户看到的界面）：Vue 3 + TypeScript + Vite + Pinia（状态）。Vue 3 是界面框架；TypeScript 是带类型的 JavaScript（写起来更不容易出错）；Vite 是启动和打包工具；Pinia 是管理"全局共用状态"的库。编辑器用 TipTap（`@tiptap/vue-3`）或 Milkdown（就是网页里的富文本编辑器，用来写小说正文）；接口客户端由 OpenAPI 生成（TS types）——意思是"和后台对话用的代码由接口文档自动生成，不用手写"。
- **数据**：SQLite（`better-sqlite3`/SQLite via SQLModel）+ LanceDB 向量。SQLite 是单机版轻量数据库；LanceDB 向量是用来存和搜"向量"（把文字转成数字特征）的库。
- **桌面（可选）**：Electron 或 Tauri —— 如果以后要出桌面版客户端，就用这两个之一来包。
- **测试**：后端 pytest + pytest-asyncio；前端 vitest + Playwright；接口 schemathesis。大意是：后端用 pytest 类工具写自动化测试，前端用 vitest 和 Playwright（浏览器自动化）测试，接口用 schemathesis 按接口文档自动校验。

### 1.2 仓库结构（monorepo）

"仓库"就是存放所有代码的地方；"monorepo"指"所有代码放同一个仓库里"，mono 就是"单一、一个"。目录树如下（`#` 后面是这个文件夹干什么的）：

```
repo/
 ├─ backend/       # 后端代码
 │   ├─ app/
 │   │   ├─ api/        # 对外接口层（只收参数/做校验/调下面的业务层，不写业务）
 │   │   ├─ services/   # 真正的业务逻辑放这儿
 │   │   ├─ agents/     # AI 写作"智能体"（writer 写手 / consistency 查一致性 / fixer 修稿/…）
 │   │   ├─ gacha/      # 抽卡引擎（抽章节、抽线索之类的玩法）
 │   │   ├─ intent/     # 意图路由（判断用户想干嘛，转给对应功能）
 │   │   ├─ deslop/     # 去AI味规则（让生成文更像人写的）
 │   │   ├─ llm/        # 大模型接入层（Gateway 网关 + providers 各家模型供应商）
 │   │   ├─ models/     # 数据模型/迁移（表结构定义）
 │   │   └─ storage/    # 存储层（StateStore 状态库 / VectorStore 向量库）
 │   ├─ tests/
 │   └─ pyproject.toml
 ├─ frontend/      # 前端代码（用户界面）
 ├─ contracts/     # 接口契约文件（"一张契约"就是接口约定，这里是唯一权威版本）
 ├─ infra/         # 基础设施配置（docker-compose、Dockerfile、Nginx）
 └─ docs/          # 本套文档
```

## 2. 编码与协作规范

### 2.1 Python（后端）怎么写

- 写类型注解（标明变量是什么类型）要完整；所有对外传的数据结构都用 **Pydantic v2** 模型定义——也就是"类型和校验规则在同一个地方定，别处不用再写一遍"。
- 路由层（接请求的那一层）**只负责收参数、做鉴权（确认身份）、调 service 业务层**，不写业务逻辑，也不直接碰数据库。就像前台只负责接待和转话，具体办事的是后面的部门。
- 报错统一用约定的错误码（见接口契约 §0.2），**禁止**直接抛一个"服务器 500"了事。这样前端和排查的人才知道到底哪错了。
- 格式化用 `ruff format`，代码检查用 `ruff check`（`ruff` 是一款又管格式又管检查的工具），类型检查用 `mypy --strict`（严格检查类型）。这些命令就像"交卷前的自检清单"。
- 命名规矩：变量/函数用小写加下划线 `snake_case`，模块名用简短短的小写名词，类名用大写开头 `PascalCase`。用统一的命名，大家看代码互相都懂。

### 2.2 TypeScript（前端，Vue）怎么写

- 接口的类型定义**由 OpenAPI 自动生成**，禁止自己手写一套重复的类型——防止"后台改接口、前端用旧类型"这种前后端对不上（俗称"接口漂移"）的坑。
- 用 Vue 3 组合式 API（写法是 `<script setup lang="ts">`）+ Pinia 管理状态；抽卡动画、流式正文这类会被多处用到的，封装成可复用组件，避免一堆参数层层传（prop 钻透）和重复代码。
- 格式化用 `prettier`，检查用 `eslint`（配 Vue 3 对应规则），类型检查用 `vue-tsc --noEmit`。
- 命名规矩：单文件组件（一个 `.vue` 文件就是一个组件）用 `PascalCase.vue`，组合式函数用 `useXxx`（use 开头），常量用大写加下划线 `UPPER_SNAKE`。

### 2.3 契约优先（Contract-First）

"契约"（Contract）就是前后端之间"就这么定"的接口约定。规则：

- `contracts/` 目录下的 OpenAPI 文件是**改之前必须评审**的单一事实源（管用的一份），前后端各自的 client/types（客户端代码/类型）都从它生成。
- **改接口唯一合法的方式**：先改契约 → 评审 → 提交 → 前后端两边重新生成代码 → CI 自动检查两边的差异是空的（也就是"完全一致"）。只要按这个流程走，前后端就不会对不上。

### 2.4 提交规范（Conventional Commits）

每一条提交记录（commit，也就是"我改了什么"的一次存档）的标题按这个格式写：

```
type(scope): subject
```

- `type`（类型）只能从这几种里选：`feat`（新功能）、`fix`(修Bug）、`refactor`（重构，不改功能只改写法）、`chore`（杂项）、`docs`（文档）、`test`（测试）、`perf`（性能）、`build`（构建）。
- `scope`（范围）写这次改动涉及哪块，`subject`（主题）一句话说改了什么。

示例：`feat(gacha): 支持盲抽揭晓动画`（意思是：给抽卡模块加了一个"盲抽揭晓动画"功能）。

如果是**破坏性变更**（改动后旧接口不能继续用、会连带着改别的地方），在 `type(scope)` 后面加个 `!`，比如 `feat(story)!: 移除 xxx`，并且要在提交说明里写 `BREAKING CHANGE:` 提醒大家。

## 3. 分支策略与协作流程

### 3.1 Git 分支模型（GitHub Flow，用 Trunk-based 简化）

"分支"（branch）可以理解成"从主线复制出来的一片私人工作区"，改完再合回来。"main"就是那个最稳定、随时能上线的主线分支。

- `main`：永远是可发布状态（绿，指测试通过）。只有合并 PR（见下）之后才更新它。
- 功能分支（做某个新功能时的分支）：叫 `feat/<issue-id>-<kebab>`，从 main 上切出来。"issue"是登记问题/任务的编号，`kebab` 是小写字母加中横线的写法。
- 修复分支（修Bug时的分支）：叫 `fix/<issue-id>-<kebab>`。
- **禁止**直接往 main 推东西；一切改动都要走 PR（Pull Request，请求合并）流程。

### 3.2 PR 流程（要把改动合进主干前，按这个步骤来）

1. 从当前最新的 main 切一个新分支，先建好对应的 Issue（编号留着，提交和 PR 里都用它做关联）。
2. 本地先把 `ruff` / `mypy` / `tsc` / `test`（各种检查和测试）跑过，没问题再进行下一步。
3. 开 PR（发起合并请求），按模板填：改动摘要 / 关联的 Issue / 测试说明 / 接口契约有没有变更。
4. CI（自动检查）必须全绿：lint 代码检查 + 类型 + 单元测试 + 契约 diff（契约差异）+ 构建都要过。
5. 至少 **1 名** 不是作者本人的人（reviewer，评审人）批准；如果是接口契约或数据模型改动，还需要 owner（模块负责人）复核。
6. 合并用 squash（把这一分支的多次提交压成一次再合并），保持主线的历史干净清晰。

### 3.3 代码评审关注点（评审 checklist，reviewer 重点看这些）

- 接口和契约是否一致（字段/枚举/错误码对不对得上）。
- 有没有偷偷加了没评级的 key/配置；有没有碰到 main 不该动的范围。
- 一致性、状态回写有没有人兜底（比如生成稿会把状态改了，这个改了的状态谁来保证不会乱）。
- 异常、越权（干没权限的事）、重放（同一请求被恶意重复发）有没有处理。

## 4. 环境与工具

### 4.1 环境矩阵

"环境"就是代码跑在哪、给谁用。三套：

| 环境 | 用途 | 地址 | 配置来源 |
|------|------|------|----------|
| dev（本地） | 日常开发 | 后端 `:8000`、前端 `:5173` | 本地 `.env`（BYOK，自带钥匙） |
| test（CI/Staging） | 自动测试 + 联调 | CI 内 / `staging.<domain>` | secrets 托管（密码等敏感信息放在专门的保管地） |
| prod | UAT/上线发布 | `https://api.<domain>` | secrets 托管，本地不落明文（本地不留密码原文） |

说明：

- 所有敏感配置（API Key 接口密钥、数据库等）都走**环境变量/secrets**（也就是存在"配置或密钥保管"里，不进代码仓库）。`docs/.env.example` 提供了一份模板，照着填就行。

### 4.2 常用命令（团队统一成这套，别各起一套）

- 后端：先 `uv sync`（把依赖装齐，sync 同步的意思）→ 再 `uv run uvicorn app.main:app --reload`（启动服务，`--reload` 是改代码自动重启）；跑测试用 `uv run pytest`。
- 前端：先 `npm ci`（按锁定版本装依赖）→ 再 `npm run dev`（起本地开发服务）；跑测试用 `npm test`；跑端到端测试用 `npm run e2e`。
- 契约：用 `schemathesis run <openapi>`（拿接口文档自动去校验实际实现符不符合）。
- 本地一键启动：`docker compose up`（一跑这个，env dev 相关的全部服务都起来了）。

### 4.3 版本控制工具（哪些东西不能提交进仓库）

- Git 的提交说明统一用 Underscore commit message（见上文 §2.4）。
- **禁止提交**这些进仓库：`node_modules/`（前端依赖包）、`__pycache__/`（Python 缓存）、`.venv/`（Python 虚拟环境）、`.env*`（环境变量文件，除 `.env.example`）、模型 `output/`（跑出来的结果输出）、`*.sqlite`（本地数据库）。这些要么是别人的机器会再装的依赖，要么是本地的密钥和临时文件，不该进版本库。
- 生成出来的东西（比如由 OpenAPI 生成的 client 类型代码）由 CI/构建流程产出，按团队约定选择不入库、或按规矩入库。

## 5. 缺陷管理流程（Bug 怎么处理）

基于 `AI 小说生成系统-开发计划与质量门禁.md` §6，落到具体工具上（比如用 GitHub Issues + Labels，即 GitHub 的问题单 + 标签）。

- **Issue 模板字段**（报 Bug 时要填的）：标题、环境（哪个环境出的问题）、严重级（P0/P1/P2/P3，P 越大越严重/越紧急）、复现步骤、期望行为、实际行为、受影响接口、相关 commit。
- **标签**：`P0/P1/P2/P3`、`bug/feature/enhancement`（Bug/功能/优化）、`contract-change`（是否涉及接口契约变更）。
- **流程状态机**（一个 Bug 的一生）：
  `New → Triaged(定级+指派) → In Progress → Fixed(提交链接修复PR) → Validate(QA) → Closed / Reopened`
  - 新登记 → 定级并派人 → 开修 → 修复完成（挂上修复 PR 的链接）→ 给 QA 验证 → 关闭 / 有问题重新打开。
- **效率约定**（多久处理完）：
  - P0：当天就得响应，修复 PR 当天提。
  - P1：3 天内提修复。
  - P2/P3：先进 backlog（待办池），排期后处理。
  - 提测（提交 Validate 验证）时**必须带复测证据**（截图/日志/用例编号），不能空口说"我测过了"。
- 涉及接口变更的 Bug，**必须同时改契约**，并给 issue 打上 `contract-change` 标签（防止契约和实现越跑越不一样）。

## 6. 结语

本文件 + 契约 + 计划，一起构成团队开工的"交通规则"。四条原则记住就行：**契约是协作边界（前后端以契约为准），main 始终可发布（主干一直能上线），异常/越权/重放必须有兜底，接口变更必走契约流程**。
