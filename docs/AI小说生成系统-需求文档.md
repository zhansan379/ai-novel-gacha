> **这份文档是干嘛的**
> 一句话：我们要做一个"AI 陪你写小说、你来决定剧情往哪儿走"的产品。读者只负责做选择、下指令，剩下写正文、保证剧情不崩、连载很多章这些活儿，全交给系统自动完成。下面这份文档就是把这些"要做的事、做到什么程度算达标、哪些优先做"清清楚楚写下来，给产品、开发、运营伙伴一起对齐用的。

## 1. 项目概述

### 1.1 一句话定位
一个以「**抽卡** / **自由输入**」来推动剧情做出决策的 **AI 互动小说生成系统**——故事每一次往哪儿走，由用户说了算；系统根据当前的故事发展到哪儿了，连续不断地把后续正文生成出来，讲得通、读得顺、没有明显的"AI 味儿"，并且可以一章一章连载很长。

### 1.2 和现有开源项目的差别（为什么我们要做这个）
我们调研了 11 个开源的写小说项目，得出一个共同结论：
- 长故事要一直记得前文、别前后打架、去掉 AI 腔，这些是普遍的难题，市面上已经有不少成熟的办法（把前面的内容分几层喂给模型、自动压缩、存一张"当前状态卡"、让多个 AI 角色分工合作、写好后用规则扫一遍）。
- 但**没有任何一个项目把"用户怎么选择剧情走向"当成核心产品来做**：
  - oh-story-claudecode / chinese-novelist-skill / kimi-writer → 剧情要么一条线走到底，要么完全自动，用户插不上手；
  - storyforge / OpenFic / denova / neuro-book / AI-Novel-Writing-Assistant → 全程都要用户手动一句一句地指挥，用起来门槛很高。

本项目把"剧情怎么选"做成一个像开盲盒抽卡一样好玩的玩法（上手简单、好玩、还有收集的乐趣），同时也保留"自由输入"（想怎么发挥就怎么发挥），并且把开源生态里最成熟的工程能力直接拿来用。

### 1.3 目标
- G1｜用户能用「抽卡」或「自由输入」这两种方式，持续又自然地把剧情推下去，全程不需要会写作、也不需要懂编程。
- G2｜生成正文：剧情连贯、前后对得上（角色不突然"失忆"、埋下的伏笔后面能收回来、时间线不搞混）、读起来顺、没有 AI 味儿。
- G3｜支持长篇连载（目标 ≥ 50 章 / 每章 2000–3000 字）。
- G4｜主要的主流开源模型（跟 OpenAI 兼容的）和本地模型都能接上，用户也可以自己带模型/密钥进来用。

### 1.4 我们不做什么（范围之外）
- 不做网文平台的上架、榜单、签约、运营，也不做收费那一套。
- 不做漫画、短剧这些跨媒介的自动改编（会预留好扩展的口子，以后想加再说）。
- 不做多人同时在线的协作编辑（V1 版本只支持单人、单个项目）。
- 不做针对某个平台风格的"强制合规过滤"，只做通用的"去 AI 味"。

## 2. 用户画像（大概是什么样的用户在用它）
| 画像 | 描述 | 核心诉求 |
|------|------|----------|
| 互动小说 / 文字游戏玩家 | 喜欢"靠选择推剧情"这一类，玩过跑团、视觉小说 | 门槛低、有惊喜、还能收集，剧情别写崩 |
| 抽卡 / 收集爱好者 | 喜欢开盲盒、集卡那一套 | 卡牌分稀有等级、有图鉴可以慢慢集 |
| 网文读者 / 轻量写手 | 想花很少力气就得到一段自己想要的故事 | 能自由输入、文风能选、能连载很长 |

## 3. 核心玩法设计（这份文档最要紧的部分）

每次剧情走到一个"剧情该分岔了"的地方，系统就暂停生成，弹出一个决策界面，让用户"二选一""多选一"来定方向：

### 3.1 抽卡（Gacha）
系统（靠模型加上当前故事讲到哪儿了）当场给你生成 **3–5 张「命运卡」**，每张卡代表一个可能的剧情走向。支持两种抽法：

- **盲抽（Draw）**：玩家看不到卡面是什么，点一下随机翻出来一张。要的就是随机性和惊喜感。
- **明选（Pick）**：一次把每张卡的卡面文案连同"这张卡会带来什么后果"的标签（比如：机遇 / 危机 / 角色 / 转折）都亮出来，玩家挑一张。

卡牌有**稀有度**（N / R / SR / SSR）：
- 稀有度高低由这张卡的剧情张力、风险回报、对主线影响有多大来决定；
- SSR 卡通常带来更强烈的冲突，或者是更大的剧情岔路（比如直接改变主线走向、牵出隐藏设定）；
- 稀有度还会影响抽中的基础概率，以及出场时的展示效果（稀有卡配上更带感的文案/场景描写）。

卡牌的常见类型（由"方向事件生成器"产生）：
- **事件卡**：推动剧情随机发生点事儿（冲突、意外、机遇）。
- **行动卡**：给主角一个选项（角色接下来怎么做）。
- **场景卡**：换场景 / 换环境。
- **相遇卡**：来一个新角色，或者人物关系发生变化。
- **伏笔卡**：埋下一个伏笔，或者把之前埋的伏笔引爆，会跟"前后一致性"那一套联动。

### 3.2 自由输入（Free Input）
玩家任何时候都可以直接敲一段文字下指令，系统会：
- 通过"意图理解"把一句大白话翻译成剧情命令（加事件、加对白、加/改设定、切场景、让某个角色出场）；
- 也可以挑一张刚抽到的卡，先在上面写一句"自定义改写"再采用（玩法可以混着来）；
- 指令被采纳后，会和"正文生成器 / 状态更新模块"配合，保证剧情仍然能自圆其说。

### 3.3 决定怎么走的兜底原则
不管你是抽了张卡，还是自己下的指令，生成器都必须让剧情**自然接上前因后果**（靠"方向采纳器 + 前后一致性校验"来兜底），不能出现"断线感"或者明显突然跳戏。

## 4. 功能需求（具体要做什么）

**优先级定义**：P0 = 首版必须做；P1 = 重要，第二版做；P2 = 可选、可以之后再加。

### FR-1 创建故事、初始化　[P0]
- 要做什么：用户丢一句话灵感/题材（或者系统随机生成一个），系统自动产出整个故事的地基：书名/标题候选、世界观设定、初始角色（主角+配角）、最初的主线方向、最初能抽的卡池。
- 怎么算达标：给出 3 套整本书的方向候选；每一套都含世界观 + 角色卡 + 一句话主线；用户能选一套，也能要求重新随机再来一次。

### FR-2 正文边打字边显示（流式生成）　[P0]
- 要做什么：按当前的故事状态、以及已经敲定的方向，把下一段正文一个词一个词地边生成边显示出来，并不断追加到当前这一章后面。
- 怎么算达标：网络正常时，从发出请求到看到第一个字，时间 ≤ 3 秒；生成过程中随时能暂停/继续；生成出来的内容自动写进项目的正文库里。

### FR-3 识别剧情该分岔的时点、并生成候选　[P0]
- 要做什么：生成器在正文写到"可以让你做决定的地方"时，自动判定这里该停下来让你选；系统接着生成几个候选方向（也就是卡池里的卡）。
- 怎么算达标：每章自然出现 1–3 个这样的分歧点；候选的方向和当前剧情要强相关（别跑题）。

### FR-4 抽卡系统　[P0 · 最核心的玩法]
- 要做什么：见前面 §3.1。生成 3–5 张卡，支持盲抽/明选、稀有度、后果标签、卡面文案展示。
- 怎么算达标：抽卡结果要随机、且概率权重可以配置；选定某张卡后能正确触发对应的方向；稀有度分级正确；卡面没有乱码、也不会长得超出界面。

### FR-5 自由输入的引导　[P0 · 最核心的玩法之一]
- 要做什么：见 §3.2。支持自由输入、对抽到的卡进行改写、以及意图理解。
- 怎么算达标：常见的指令（加角色/加事件/加设定/切场景/抛伏笔）能被系统听懂并真正生效；明显跑题的输入会给一句提示，但用户坚持的话也允许；改写后再采用，不会破坏剧情的一致性。

### FR-6 前后一致 / 状态维护　[P0 · 底线]
- 要做什么：一直维护一份"世界状态 + 角色状态 + 时间线 + 伏笔账本"（伏笔账本 = 专门用来记"埋了哪些伏笔、谁被回收了"的清单），每回生成前读它、生成后更新它，避免角色突然失忆，保证伏笔能收得回来。
- 怎么算达标：随机抽 20 个角色的属性/设定项，跨 30 章抽查都不能有前后矛盾；埋下的伏笔在用户触发时能正确回收/兑现；时间线不能出现前后打架的地方。

### FR-7 文风、去掉 AI 味　[P1]
- 要做什么：提供几种文风预设（可选），并对生成好的稿件做一轮"去 AI 味"的规则扫描（把模板句、机械转场、公式化的表达挑出来），分"拦截"和"建议"两种结果给用户。
- 怎么算达标：拿示例稿件去过一遍"去 AI 味"扫描，不能命中 0 分档的违禁项；至少提供 3 种文风预设。

### FR-8 记忆与长故事上下文　[P1]
- 要做什么：分几层喂前文 + 自动压缩 + 每章给个摘要 + 关键事实的检索（"本地离线检索"：在一大堆历史里精确找到某个设定/伏笔，属于可选），用来支撑长篇连载。
- 怎么算达标：单章的正文用的量不超过模型一屏装得下的 80%；长故事里早期出现的关键设定/伏笔，到后面还能被系统想起来；花了多少"量"要在用量面板里看得见（这里的"量"就是按上屏字数/计算量计费的那种小单位）。

### FR-9 存档 / 分支 / 回溯　[P0]
- 要做什么：自动存档；支持从任意一个历史决策点"重来"（回到某个选过的分歧点，重新抽卡/重新输入，走出另一条剧情分支）；也能往后退一步。
- 怎么算达标：能回溯到任意已经发生过决策点，并且走出一条新分支；回退/开新分支不影响其他项目；每一条分支都能起个名字。

### FR-10 接多个模型（自带密钥）和控制成本　[P1]
- 要做什么：模型的接入统一走跟 OpenAI 兼容的口子，支持多家服务商 + 本地模型（比如 Ollama）；不同任务用不同模型；有"用量预算保护"和"用量统计"。
- 怎么算达标：能配置至少 3 家服务商 + 本地模型；不同的任务用不同的模型/温度（"温度"= 控制模型写得保守还是放飞的一个参数）；用量达到预算上限会自动提醒 / 暂停。

### FR-11 用户界面　[P0]
- 要做什么：以 Web 界面为主（之后可以再加桌面端/手机端/网页应用）。包含：项目列表、故事读写页（正文 + 边生成边显示）、**决策页（抽卡动画/明选/输入框）**、设定/角色/伏笔的查看页、图鉴收集、历史/分支查看。
- 怎么算达标：从开始到完成一次抽卡，点击 ≤ 3 次就能搞定；正文能读、能滚动、能复制；整个流程不用刷新页面。

### FR-12 自己审稿 / 质量反馈　[P1]
- 要做什么：生成之后可以进入"审稿-修复"流程：系统给出一份结构化的审稿报告（讲连贯性 / 设定吻不吻合 / 文笔），用户一键提交修复。
- 怎么算达标：审稿报告里要列出问题，并且指出对应正文里的证据（具体哪句话）；一键修复能替换掉相应的文本，其余内容保持不动。

### （P2 可选，之后再说）
- 卡牌图鉴收集、以及稀有度收藏进度。
- 角色属性会影响抽卡的倾向/权重。
- 结局统计 / 分支树画出来给人看。
- 多人在线房间、公开发布分享。

## 5. 非功能需求（运行起来要满足的硬性要求）

| 类别 | 需求 |
|------|------|
| 性能 | 出第一个字的时间 ≤ 3 秒；单次生成不能让界面卡死；同时有 10 个用户用也不会有明显变慢 |
| 可用性 | 生成中途能暂停/恢复；进程异常断了也能断点接着来（存档放在 S3 上） |
| 可扩展 | 模型接入做成插件式，想加就能加；任务可以按需加"分工的 AI 角色"；能加新的文风/卡类型 |
| 数据安全 | 本地优先，项目数据默认存在用户自己的端上；云端模式是可选开关；不会拿正文去训练模型 |
| 成本 | 提供用量看板看得见花了多少"量"；靠自动压缩 + 按需从本地抓取，把成本压下去 |
| 兼容 | 前端主流浏览器都能跑（Chrome/Edge/Firefox）；可选做手机端网页 / 用 Capacitor 包成 APP（Vue 生态的移动端方案） |
| 可维护 | 后端接口要做成文档化的（按 OpenAPI 标准，方便查）；要有日志和监控 |

## 7. 成功指标（能用数字量化的"做到没做好"）
- 第一次用就完整生成出整个故事的概率 / 完成率。
- 从每个决策点出现到用户做完决定的平均耗时（目标 < 30 秒）。
- 抽完卡后剧情"接得自然不自然"的用户主观打分（抽样问卷 ≥ 4/5 分）。
- 连续 20 章里的前后不一致错误数量（目标 ≤ 2 处重大矛盾）。
- 过"去 AI 味"规则扫描的通过率。
