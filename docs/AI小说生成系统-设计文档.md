# AI 小说生成系统 设计文档

> 文档版本：v1.0　|　日期：2026-09-20
> 关联需求：`AI 小说生成系统-需求文档.md`
> 设计依据：基于 11 个开源小说生成项目的工程经验（见《小说生成开源项目调研报告.md》）

---

> **这份文档是干嘛的：** 它解释我们这个"AI 小说生成器"是怎么搭起来的——分成哪几块、每块用什么技术、某个环节背后是怎么运转的、数据存在哪里长什么样。下面把原文里的专业说法都换成大白话，方便非技术同事也能看懂整体思路。记住几条主线索就好：**先出玩法（抽卡/打字）→ 定剧情方向 → AI 按方向继续写，并且前后不打架、读起来不像 AI 写的、看出戏也能修。** 技术细节看需要，不用记。

---

## 1. 想达到的目标
- 支撑「抽卡 / 自由输入 → 决定剧情走向 → 生成连贯长篇」的核心玩法。
- 尽量复用开源生态里最成熟的做法，不重新造轮子：
  - **多级内容注入 + 自动压摘要**（参考 OpenFic / AI-Novel-Writer / denova / kimi-writer）
  - **一张"当前进度状态卡"**（结构化 Story State，参考 oh-story-claudecode / denova / NovelClaw）
  - **多个 AI 角色分工协作的生产流水线**（参考 oh-story / denova / neuro-book / AI-Novel-Writing-Assistant）
  - **"去 AI 味"的自动检查**（参考 neuro-book llmlint / storyforge anti-ai-adapter）
  - **同一套接法接多个模型 + 用户自己填密钥（BYOK，自带钥匙进系统）**（参考各项目都走 OpenAI 兼容协议）
  - **默认本地跑、也能选云端**（参考 AI-Novel-Writer / storyforge）

## 2. 整体怎么分块（总体架构）

```
 ┌────────────────────────────────────────────────────────────┐
 │                   前端界面 (Vue 3 + Vite + Pinia)           │
 │  项目列表 │ 故事读写页(边写边出/流式) │ 决策页(抽卡/输入) │ 设定/图鉴 │
 └──────────────▲─────────────────────────────────────────────┘
                │ 网页通讯：普通请求 (REST) + 逐字推送 (SSE) / 实时互动 (WebSocket)
 ┌──────────────┴─────────────────────────────────────────────┐
 │                      接入层 (FastAPI)                       │
 │   项目/故事/章节/决策/卡片 等各类网页入口                     │
 │   抽卡 / 流式生成 / 撤销 / 分叉 / 修改重写                    │
 └──────────────▲─────────────────────────────────────────────┘
                │
 ┌──────────────┴─────────────────────────────────────────────┐
 │                AI 编排层 (LangGraph)                         │
 │                                                             │
 │  总调度 Orchestrator（统管下面每个分工）                       │
 │   ├── DirectionGenerator  写剧情走向 → 生成候选卡片(3-5张)    │
 │   ├── IntentRouter        理解「自由输入」想干什么            │
 │   ├── WriterAgent         写下一段正文(边写边推给前端)         │
 │   ├── ConsistencyChecker  检查前后文有没有矛盾/没收的伏笔/时间乱 │
 │   ├── FixerAgent          针对问题定点修补                    │
 │   ├── DeslopLint          扫"AI 腔"规则检查                  │
 │   └── Summarizer          给章节写摘要 / 压摘要               │
 └──────────────┬─────────────────────────────────────────────┘
                │
 ┌──────────────▼───────────┐  ┌──────────────────────────────┐
 │       状态库 StateStore  │  │  向量库 VectorStore (可选)     │
 │  故事 │ 角色 │            │  │  LanceDB / Qdrant / SQLite FTS│
 │  时间线 │ 伏笔 │           │  │  搜"关键设定/伏笔"用的本地检索 │
 │  卡池 │ 决策记录 │          │  └──────────────────────────────┘
 │  (SQLite + 文件系统)       │       ▲
 └──────────────▲───────────┘       │
                │                  本地离线检索
 ┌──────────────┴───────────┐  ┌──────────────────────────────┐
 │    多模型接入层 LLM Gateway│  │       存储层 Store            │
 │  统一接 DeepSeek/OpenAI/  │  │  状态存 SQLite + 正文存本地文件│
 │  Ollama 等，按任务挑模型   │  │  + 对象存储(云端模式可选)       │
 │  + token 用量预算         │  └──────────────────────────────┘
 └──────────────────────────┘
```

**这么分层的用意**：决定剧情走向的模块 与 写正文的模块 相互独立（决策只产出一个"往哪走"的方向；写正文的模块就照着这个方向写），所以"抽卡"怎么变都不会影响底层的生成和存储。接多家 AI 模型时，用一层统一的"中转网关"挡住各家差异。状态库和正文分开存，既能保证前后一致，正文又是人能直接读的文件。

## 3. 用哪些技术（含选它的理由）

| 组件 | 选型 | 参考开源项目 | 理由 |
|------|------|--------------|------|
| 后端框架 | Python 3.12 + FastAPI | OpenFic / NovelClaw | 天生适合"边写边推"的流式；围绕 AI 的生态成熟 |
| AI 编排 | LangGraph / LangChain | OpenFic / AI-Novel-Writing-Assistant | 原生支持流水线式、断点续跑、多个 AI 分工并行 |
| 前端 | Vue 3 + Vite + Pinia + TipTap（@tiptap/vue-3，或换 Milkdown） | neuro-book（同领域 Vue 先例）/ storyforge | Vue 生态成熟，状态管理、组合式 API、编辑器组件都有官方 Vue 支持，容易做流式/抽卡动画；**neuro-book 已用 Vue3+Nuxt+TipTap/Milkdown 实证过小说编辑场景** |
| 桌面版（可选） | Electron 或 Tauri | AI-Novel-Writer | 想完全本地跑时可选 |
| 状态库 | SQLite（Prisma/SQLModel）+ 文件系统 | denova / oh-story | 轻量、不用运维、事务可靠；正文用文件存方便人读 |
| 向量/检索 | LanceDB（两种检索方式混用：按语义相似 + 按关键词），可选 Qdrant | OpenFic / AI-Novel-Writer | 本地存词向量、不用连云；混合检索兼顾"找得准"；还留了关键词检索兜底 |
| 模型接入 | 统一接法（OpenAI 兼容协议）+ 用户自带密钥 | 全系 | 兼容 DeepSeek/OpenAI/Ollama/Groq/OpenRouter 等，按任务挑便宜/合适的模型 |
| 上下文 | 自研三层上下文（L0/L1/L2）+ 自动压摘要 + 状态卡 | AI-Novel-Writer / OpenFic | 内容分层次注入 + 控制每次调模型的量，见 §7 |
| 去 AI 味 | 规则库检查（脚本级）+ 模型语境复核 | neuro-book llmlint / storyforge | 秒速扫全稿 + 结合上下文判断，避免只靠模型"感觉" |
| 部署 | Docker Compose 本地 + 可选云 | storyforge / OpenFic | 一键启动，用户自带密钥，不用买账号 |

## 5. 核心流程：事情是按什么顺序走的

### 5.1 一本小说怎么开局的（FR-1）
```
一句灵感 → 让模型生成 3 套「整本方向 + 书名」
  → 用户挑一套（或不满意，重新抽）
  → 模型生成 世界观设定 + 初始角色(主角/配角) + 主线一句话
  → 写进状态库(故事/角色/大纲) + 生成初始卡片池
  → 进入正文生成
```

### 5.2 怎么写下一段正文（没有决策、直接往下推的流程，FR-2）
```
写书的循环：
(当前状态 S, 当前章) → 写正文的模型写下一段(边写边推给前端)
  → 检查前后文一致性的模型 对比状态变化 → 去 AI 味的模型做检查
  → 有"挡路"的问题 → 修补模型去修 或 要求重写（最多 3 次）
  → 更新状态 S（角色状态/伏笔/时间线/正文）
  → 章够了长度 / 剧情收尾 → 结束本章 → 摘模型生成章摘要
```

### 5.3 决策流程（核心，FR-3/4/5）——按时间顺序
```
① 发现「分歧点 D」出现在正文末尾（看剧情张力/推进信号或用周期判断）
② 生成方向的模型输入 (当前状态, 分歧点, 文风) → 产出 卡池 3~5 张卡
      每张卡 = {编号, 标题, 卡面文案, 后果标签[机遇/危机/角色/转折/伏笔],
               稀有度(N/R/SR/SSR), 权重, 方向说明 direction_spec}
③ 前端进入「决策页」：
     模式A 盲抽：用户点抽 → 抽卡引擎按权重 + 稀有度概率随机抽出一张 → 揭晓动画
     模式B 明选：同时展示卡片，用户点选一张
     模式C 自由输入：用户打一句话 → 意图识别模型看懂 → 可能回填/改写某张卡后用
④ 采用的方向 = 抽到的卡 或 用户指令 或 改写后的卡
⑤ 写正文模型以 (当前状态, 分歧点, 方向) 写下一段 → 走 5.2 的一致性/去AI味检查
⑥ 决策记录模块 记下这次(卡编号/模式/方向/时间/分支标记)——供回溯和分支用
⑦ 更新当前状态，继续往下写
```

### 5.4 抽卡引擎怎么设计的（FR-4）
- **出卡用的一段指令（Prompt）**：给模型「当前故事状态摘要 + 上一段正文 + 文风 + 允许的卡类型」，要求它输出固定格式的 JSON。（格式要求很严；多卡尝试设了冷却，防止刷。）
- **权重怎么定**：按稀有度给底子权重（N:70 / R:25 / SR:5 / SSR:1 之类的，可配）；可以叠加"角色喜好"修正（后期收集到角色卡后，按角色性格给权重打折）。
- **盲抽的随机性**：真随机数（在服务器端产生，防止刷）；AI 只参与"生成卡"，不参与"抽哪张"。
- **防止抽到"神卡"但剧情断线（稀缺卡风险评估）**：出高稀有度（SSR）卡时强制要求带 `risk_balance` 字段（剧情张力 + 建议的后转折），降低"抽到神卡却接不下去"。
- **兜底（自然接续）**：抽到的卡和后面写出来的正文打架了，由 一致性检查 + 修补 两个模型自动调和，界面上给个轻提示"剧情已自然接续"。

### 5.5「自由输入」怎么读懂你在说什么（FR-5）
意图分类（意图识别模型）：
| 意图 | 示例输入 | 怎么处理 |
|------|----------|------|
| 加事件 | "让主角发现一张藏宝图" | 注入事件 → 生成对应场景 |
| 加角色 | "出现一个会算命的猫" | 建角色卡 + 出场场景 |
| 换场景 | "切到城市夜景的街角" | 覆盖场景/环境 |
| 加设定 | "这个世界有禁魔湖" | 写世界观 + 可选埋个伏笔 |
| 加角色特点 | "让女主更毒舌" | 更新该角色的状态卡 |
| 定结局方向 | "我要走向悲剧结局" | 改主线/收束方向 |
| 分不清 / 跑题 | 无法归类 | 返回类似卡片的澄清选项，允许用户硬上 |

统一输出：一个"方向说明"（`direction_spec`，比抽卡卡片更结构化的指令），交给写正文的模型消费。

## 6. 数据都长什么样（数据模型，核心表）

```
Project(项目, 用户, 标题, 创建时间, 版本)
 ├─ Story(故事, 所属项目, 一句话灵感, 类型, 简介, 文风档id, 状态)
 ├─ Outline(大纲, 所属故事, 层级[卷/幕/章], 标题, 顺序, 目标)
 ├─ Chapter(章, 所属故事, 所属大纲, 序号, 标题, 摘要, 字数)
 ├─ Passage(段, 所属章, 顺序, 内容, 关联决策?, 状态[生成中/定稿])
 ├─ Branch(分支, 所属故事, 关联决策, 名字, 创建时间)   -- 回退后开出的新分支
 ├─ Character(角色, 所属故事, 名字, 角色定位, 特点, 状态(json), 头像?, 剧情弧)
 ├─ CardPool(卡池, 所属故事, 关联决策, 卡片们(json[]))   -- 出卡那一刻的卡池快照
 ├─ Decision(决策, 所属故事, 关联段落, 决策序号, 模式[抽卡/点选/自由输入],
 │           卡编号?, 方向说明(json), 结果摘要, 创建时间)
 ├─ Foreshadow(伏笔, 所属故事, 内容, 埋下时间, 状态[已埋/推进中/已回收],
 │             回收时的段落编号?)
 ├─ TimelineEvent(时间线事件, 所属故事, 内容, 第几天?, 顺序号, 来源)
 ├─ WorldState(世界状态, 所属故事, 状态(json), 版本号)    -- 记录每次变化 + 版本
 ├─ StyleProfile(文风档, 名字, 系统指令引用, 去AI味规则, 温度)
 └─ UsageLog(用量日志, 所属项目, 任务, 模型, 输入/输出量, 花费美元, 时间)
```

几个要点：
- **故事的状态采用"往里加/追加"式**：每次生成，把产生的新事实、变化写进 世界状态 / 角色状态，并保留版本号，方便回退后重建。
- **决策记录 + 段落关联**：实现"分支/回溯"——从某个决策往后派生新分支，这条分支后面的段落就复制一份。
- **卡池快照**：把出卡那一刻的完整卡组存下来，方便"图鉴"收集和复现。

## 7. 怎么记上下文、怎么不"忘"（FR-8）

采用**三层上下文 + 一张状态卡 + 自动压摘要**（结合各开源项目的最佳做法）：

- **L0 常驻（约 500–1000 token）**：项目/故事总览：书名、类型、当前主线一句话、核心角色一句话列表、当前章节号。*（token 可以当成"一次喂给模型的字数额度"，越小越省。）*
- **L1 编辑器/正文相关（约 1000–3000 token）**：当前章节已生成的正文（写正文的模型用来模仿文风、接上下文）；在决策页时换成"上一段正文 + 当前分歧点的描述"。
- **L2 用的时候才临时拉（按需/检索）**：写正文的模型通过工具，按需去读：当前章大纲、相关角色的完整状态、相关的伏笔、关键设定（从向量库或按编号精确取）。
- **状态卡（结构化的当前状态）**：维护一份"当前世界/角色/伏笔/时间线"的紧凑 JSON 状态卡（参考 oh-story，上限 12KB、不放进正文指令里），每次生成后由一致性检查模型回写。
- **自动压摘要**：当累计喂给模型的量接近上限（如 85–90%）时，触发摘模型把"最早章节"压成摘要（参考 kimi-writer 的阈值 / OpenFic 的触发比例）。
- **本地离线检索的用途**：跨了很长篇章后，写正文的模型需要"真正很早以前的某个设定/伏笔"时，用"按意思找相近"的检索召回（LanceDB 混合索引），并在喂给模型的指令里标注来源。

## 8. 怎么去除"AI 腔"（FR-7，参考 llmlint / anti-ai-adapter）
- **一套规则库**：内置几类常见 AI 腔——
  - 填充词/口头禅、机械过渡（"然而/与此同时/值得一提的是"）、公式化的设问、处处二元对立、空泛的总结、呆板的句式重复、过度解释内心的"AI 腔"。
- **两级检查**：先用静态规则秒速扫全稿（扫中即分等级：挡路级/建议级）+ 再用少量模型做上下文复核（判断这块是不是真有 AI 腔，避免误伤）。
- **输出**：定位到哪句 + 解释原因 + 替换建议（可以直接拿去修补模型修，或等用户点头采纳）。
- **文风预设**：文风档（如"金庸武侠/都市爽文/沉稳克制冷叙事"）注入系统指令，控制用词、对话风格、叙述距离（参考 storyforge writing-styles）。

## 9. 网页入口到底有哪些（API 与流式设计，摘要）
- 原则：普通请求（一锤子买卖、同步）+ 流式（正文边写边推给前端）。
- 关键入口：
  - `POST /stories`（创建/初始化一本书）
  - `POST /stories/{id}/generate/stream`（正文流式生成，边写边推，可带可选方向）
  - `POST /stories/{id}/decisions/{no}/cards`（生成卡池）→ `POST .../decisions/{no}/apply`（采用卡或输入）
  - `GET /stories/{id}/state`（看当前状态卡：角色/伏笔/时间线）
  - `POST /stories/{id}/decisions/{no}/undo|branch`（回退/开新分支）
  - `POST /stories/{id}/passages/{id}/revision`（审稿-修复）
  - `GET /projects/{id}/usage`（看用了多少 token）
- 出错/降级：模型限流 → 自动缓存重试并降级到低档模型；偶发失败返回"可恢复的候选"（正文存成草稿）。

## 10. 怎么部署运行
- **本地（默认）**：Docker Compose 一键起（接入层 + 前端 + SQLite 挂在磁盘上），或者用源码 `uv` + `npm dev` 跑；用户在界面里填自己的 AI 密钥（自带钥匙）。用源码跑时，打开前端页面就能操作。
- **远程模式（可选）**：挂一个对象存储来存正文；把检索库换成托管的 Qdrant；支持多项目共用。
- **桌面版（可选）**：Electron/Tauri 把前端包成桌面应用，主进程里跑 SQLite，参考 AI-Novel-Writer 的本地优先方案。

---

## 11. 分几步做出来（演进路线，按需求优先级）
- **MVP（P0，第一版先做出来）**：开局 + 正文流式 + 分歧点 + 抽卡(盲抽/明选) + 自由输入 + 基础一致性 + 存档/回退/分支 + 决策页界面 + SQLite。
- **V1.1（P1，第二档）**：去 AI 腔检查、长上下文（L2+检索）、自动压摘要、审稿-修复、多模型 + 自带密钥 + 用量看板。
- **V2（P2，再往后）**：卡牌图鉴收集、角色属性影响抽卡权重、分支树可视化、结局统计、可选多人在线。

## 12. 风险与对策
| 风险 | 对策 |
|------|------|
| 抽到高戏剧性的卡导致剧情接不下去 | 高稀有度（SSR）卡强制带风险平衡字段 + 修补模型自动调和 + 界面轻提示 |
| 长文喂给模型的量膨胀 / 成本高 | 三层上下文分层 + 自动压摘要 + 按任务挑模型 + 用量预算告警 |
| 前后矛盾（吃书/没收的伏笔） | 每次生成都对比结构化状态卡 + 一致性检查模型 + 来源标注明确 |
| 出卡跑题或太随机 | 强格式约束 + 出卡指令与当前状态强相关 + 卡池重抽 |
| 模型厂商故障 | 中转网关多厂商降级 + 本地模型兜底 |
| 依赖大型框架导致部署太重（参考 NovelClaw 的教训） | 检索库默认用 LanceDB/关键词检索的本地方案，避免硬依赖沉重的框架全家桶 |
