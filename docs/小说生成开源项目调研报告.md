**一句话横向小结**：这 11 个项目分成三大类——

- **轻量技能包类**：`oh-story-claudecode`（写长文连续性好）、`chinese-novelist-skill`（最简单），都是借用你已经装好的编程助手/Claude Code 的能力，不另外搭后台。
- **功能完整的工作台类**：`AI-Novel-Writing-Assistant`（自动化功能最全）、`OpenFic`（底层技术最新）、`AI-Novel-Writer`（最看隐私本地优先）、`denova`（最像完整写作软件）、`storyforge`（纯网页最好部署）、`neuro-book`（工程化/去 AI 味最强）、`NovelClaw`（记忆账本 + 运行过程能看到）。
- **实验/代写工具类**：`terminal-velocity`（看看 AI 全自动写小说并出版能走多远，工具属性弱）、`kimi-writer`（命令行一键自动量产）。

## 三、逐项目详解

### 1. oh-story-claudecode（ZenStory AI，~7000 star）

**磁盘路径**：`novel_projects/oh-story-claudecode`

**它是干嘛的**：一套给网文作者用的"技能包"，以 13 个技能的形式"装进"你已经在用的编程助手（Claude Code、Codex、ZCode、OpenCode 等 8 种都行），可以打通「扫榜→拆文→搭大纲→写正文→去 AI 味→生成封面」整条网文流程，主打商业化网文和写长文不跑偏。

**技术层面**：产品本身是 Markdown（写作方法和流程约定）+ Node/Python 检查脚本，不算是"跑起来的程序"，不需要显卡、不用自己配模型（直接用助手的模型）；只有生成封面单独调一次 GPT 画图。

**目录结构**：`skills/`（13 个技能，每个含操作说明 + 参考资料库）、`docs/`（架构/去 AI 味/连续性方法）、`scripts/`（自动化检查与测试）、`demo/`、`tests/`、`.claude-plugin/`、`.zcode-plugin/`。

**它怎么做到的**：
- **把文件当记忆**：每本书拆成 `设定/大纲/正文/追踪/对标/参考资料` 独立文件夹；`追踪/_tracking-state.json` 是唯一的权威记录，用来生成续写卡片、伏笔视图、角色状态、`作者知道什么 / 读者知道什么`双时间线。续写状态卡固定 7 栏、硬顶 12KB，不会塞进正文提示词；每章记录 ≤3072 字节。
- **7 个专业角色分工**：故事架构师、正文写手、一致性检查员（专门盯着剧情和伏笔）、角色设计师、联网查资料员、剧情探索、章节抽取。
- **8 个自动化守门环节保证质量**：其中只有"写正文前必须有细纲"这一条是强制的，其余都是提示建议。
- **去 AI 味**：`/story-deslop` 是一个本地确定的写作检查工具，逐条匹配已知的 AI 句式/标点/套话（check-ai-patterns.js、check-degeneration.js、normalize-punctuation），结果分"必须改"和"建议改"两档。
- **不用检索/向量库**，不靠聊天记忆，靠文件系统 + 状态记录保证前后一致，这是它最核心的机制。

**怎么用**：`npx skills add zenstory-ai/oh-story-claudecode -y -g` 安装，然后在你写作项目的根目录运行 `/story-setup` 部署守门、角色、参考资料。不需要额外 API key。

**成熟度**：工程化和自动化极强、中文网文商业向（起点/番茄/晋江/知乎盐言）、长文连续性的机制是同类里最深入的。局限：很依赖编程助手这个外壳，没有独立的云端网页版。

### 2. chinese-novelist-skill（PenglongHuang，~3100 star）

**磁盘路径**：`novel_projects/chinese-novelist-skill`

**它是干嘛的**：专门服务"想坚持写完一本完整中文小说"的 Claude Code 技能包（v2.0），核心卖点：三层递进式问答、记住你的偏好、中途断了能续写、三种写作模式、自动校验。

**技术层面**：就是 Claude Code 技能包（操作说明 + 参考资料/写作指南 + 1 个 Python 数字数脚本），全靠提示词 + 分阶段流程驱动，没有独立后台/接口/界面。

**它怎么做到的**：
- **分阶段走流程**：第 0 步初始化（读偏好、检测有没有中断的续写）→ 第 1 步三层问答（先必答 3 个核心定位问题，再可选答 5 个深度定制问题 + 生成标题）→ 第 2 步规划确认（7 列章节大纲 + 人物档案 + 写作计划）→ 第 2.5 步选写作模式（串行 / 几个角色并行 / 角色小组）→ 第 3 步疯狂创作（全自动逐章：写前分析→写 3000~5000 字→润色去 AI 味→检查字数→更新摘要）→ 第 4 步自动校验（字数和连贯性，不合格最多自动重写 3 轮）。
- **记忆/一致性**：跨会话记住你的偏好 `user-preferences.json`；每章重读大纲对应的规划并维护摘要；内置"每章要爽/悬念承上启下"这类黄金法则。
- **不用检索/向量/编排库**，全靠 Claude 本身的能力。

**怎么用**：放到 `~/.claude/skills/` 或用 `npx skills add`；用 Claude Code 的模型，没有独立界面，免额外 key。

**成熟度**：轻量、对中文友好、专治"写不完/拖稿"这个痛点、上手极快。局限：很依赖 Claude Code、机制比较浅，适合中小篇/第一部小说。

### 3. AI-Novel-Writing-Assistant（Biz Novel Studio，~3000 star）

**磁盘路径**：`novel_projects/AI-Novel-Writing-Assistant`

**它是干嘛的**：面向"完全不懂写作的新手"的 **AI 导演式长篇生产系统**——给一句灵感就能开整本书，自动套导演 + 整本生产主链 + 写法引擎 + 本书世界设定 + 检索，把"生成章节/审核/修复/状态回填"串成一条能暂停能恢复的生产线，还带漫画/短剧衍生工坊。

**技术层面**：pnpm 多模块工程；前端 React 19 + Vite + Pluto（编辑器）+ TanStack Query；后台 Express 5 + Prisma + Zod；AI 编排 LangChain + LangGraph；数据库 SQLite（Prisma 可切 PostgreSQL）；检索用 Qdrant；桌面用 Electron。

**它怎么做到的**：
- **多服务商大模型路由**：OpenAI / DeepSeek（默认）/ Anthropic / SiliconFlow / xAI，按任务（策划/写作/审核/修复/摘要…）分别路由到不同模型，温度也按任务给定（如策划 0.3、写作 0.8、审核 0.2）。
- **自动导演开书**：从一句灵感生成多套整本方向和标题组 → 定书本大方向 → 角色 → 分卷策略 → 节奏板 → 章节清单 → 逐章执行，全自动。中途遇到模型不可用/额度用完/连续失败会主动停机，并从检查点恢复。
- **章节执行主链**：写正文 → AI 审核 → 修复 → 记质量债 → 把角色状态/事实/伏笔回填 → 进入下一章；角色"资源账本"按每章出场的角色精准筛选，避免把所有角色一股脑塞进提示词。
- **检索**：Qdrant + 把资料转成向量索引（流式并行建索引、去重、检索过程可查），拆书结论也进索引。
- **写法引擎 + 反 AI 规则**：可保存/编辑/绑定/复用的写法资产；能从现有文本提取写法特征 + 原文样本形成特征池；反 AI 规则减少"模板感/解释感"。

**怎么用**：Node ^20.19 + pnpm ≥10.6；`cp server/.env .`、`pnpm dev`（网页 5173 / 后台 3000）；至少需要一个 AI 大模型的 API key，检索需要 Qdrant（可用 `RAG_ENABLED=false` 跳过）；有 Dockerfile，桌面正式版可直接下载。

**成熟度**：功能最全、深度最成熟、对中文友好、有桌面端。局限：**AGPL-3.0 双许可**（商用当 SaaS 卖需要跟作者拿授权）、依赖重、部署复杂。

### 4. terminal-velocity（mind-protocol，~1100 star）

**磁盘路径**：`novel_projects/terminal-velocity`

**它是干嘛的**："全球第一部由 AI 分工团队自己写成并出版的小说"（约 10 万字，已上架 Amazon）。这个仓库本身更像是**成品 + 创作过程的记录档案**，真正干活的核心是外部的 **KinOS (v6)** 这个自主 AI 操作系统。

**技术层面**：KinOS（基于 Claude-3，独立仓库）；本仓库里只有少量 Python 辅助脚本 + 文档 + 手稿，**没有程序代码 / 没有界面**。

**目录结构**：`complete_manuscript.md/.txt`（成品手稿）、`story/`（act1-4、场景、结构、全局时间线）、`characters/`、`world_building/`（含 tech-tree.yml）、`documentation/`、`scripts/`、`monitoring/`。

**它怎么做到的**：10 个分工角色组成团队（设定 / 生产 / 管理 / 评估 / 编年史 / 文档 / 去重 / 冗余 / 整合 / 写作 + 研究员），多角色自主协作、全程不用人盯，全程直播 + 到处提交记录透明。前后一致靠角色文件、世界设定、全局时间线 + 角色分工去重纠错，不用现代检索。

**怎么用**：当手稿可以直接读；创作侧由 KinOS 跑，本仓库不做独立部署。

**成熟度**：实验性和叙事价值大（已出版、社区关注度高）。局限：可复用性/工程化很低，核心代码在外部仓库，更像实验记录而不是工具。

### 5. OpenFic（syrizelink，~1100 star）

**磁盘路径**：`novel_projects/OpenFic`

**它是干嘛的**：跨平台、数据优先留在本地的 AI 原生"跟着感觉写"一站式小说工具——让 AI 深度参与设定/角色/伏笔维护、发散思路、协同编辑，而不是"一键生成整本"；允许按你的写作流程高度自定义提示词、角色和流程。

**技术层面**：后台 Python 3.12 + FastAPI + LangChain/LangGraph 1.x；网页 React + TipTap + TanStack Query；桌面 Electron；数据库 SQLite；检索用 LanceDB（多种检索方式混合）+ fastembed 本地转索引；模型按 models.dev 目录接入。

**它怎么做到的**：
- **每个角色是一个独立循环**：每个角色都是独立编译的 LangGraph 循环；统一超时/重试/错误分类入口。
- **内置角色用 YAML 定义**（写手、审稿、策划、审计、演员、编排…），里面带大量中文写作方法论（白描禁修辞、禁词表、"活人感写作"、反裸时间词开场）。
- **上下文管理**：多层上下文 + 自动压缩窗口 + 动态截断 + 稳定缓存；独立记忆系统做章节摘要。
- **"能检索的 Agent 式 RAG"**：LanceDB 转向量索引 + 全文检索，目标支持百万字项目内快速找回内容；数据优先留本地（零云存储）。
- **多模型 + 省钱优先**：OpenAI/Anthropic/Google/Groq/Mistral/DeepSeek/OpenRouter/Ollama + 任意 OpenAI 兼容接口。

**怎么用**：`docker run -d -p 8000:8000 ghcr.io/syrizelink/openfic:latest`，或 `pip install openfic && openfic serve`，或直接下载桌面正式版；模型 key 在界面里配。

**成熟度**：工程成熟、功能完整、开源基础设施最现代（LangGraph 1.x + LanceDB + Pydantic v2）。局限：上手/配置成本较高，主张"人写为主、AI 辅助"，不是一键整本。

### 6. AI-Novel-Writer（EthanYoQ，"Vela"，~1000 star）

**磁盘路径**：`novel_projects/AI-Novel-Writer`

**它是干嘛的**：面向 AI 写长篇的**数据全留本地的桌面工作台**，把「前提 → 角色 → 世界观 → 章节蓝图 → 草稿 → 审稿 → 修稿 → 定稿」组织成一条可追溯的流程；数据存在你自己的电脑上。

**技术层面**：Electron + React 19 + TypeScript + Vite；存数据用 better-sqlite3；检索用 LanceDB + OpenAI/Gemini 转索引；编辑器 Monaco/CodeMirror；状态管理 zustand。

**它怎么做到的**：
- **模型协议**：OpenAI 兼容（OpenAI/DeepSeek/Ollama/NovelAI）+ Gemini 原生两类；每个模型配置带温度；配置存 `~/.vela/models.json`。
- **多角色循环**：工具注册 + 结果解析 + 反复操作循环（最多 8 轮），15+ 个工具（读蓝图/读角色/读草稿/搜索知识/启动流程…）。
- **三级上下文注入**：L0 常驻约 500 字（项目总览）→ L1 编辑器感知约 800 字 → L2 按需调工具拉取，带字数预算保护，不一次塞太多。
- **长文一致**：围绕当前章节蓝图 + 相关角色 + 世界观 + 历史摘要组织；**来源写清楚的连续性材料**（作者自己填的 / 模型动态状态 / 旧项目来源不明的分开记）。
- **审稿-修稿闭环**：结构化审稿报告 + 逐项目标审稿，"待核实"项不算通过、要作者确认。
- **检索/知识库**：LanceDB 转索引检索；没配置转索引时退化成全文检索；能导入多种格式的参考文本来建仿写指南。

**怎么用**：从 GitHub 正式版下载安装（Windows .exe / macOS .dmg）；key 在界面配，或用 Ollama 本地模型免 key；开发 `pnpm install && pnpm dev`。

**成熟度**：本地优先、隐私安全、模型自由度高、审稿-修稿闭环很实在。局限：GPL-3.0、只支持 OpenAI 兼容 / Gemini、以桌面为主没有在线版。

## 四、共性实现机制分析

横向对比 11 个项目，能看出写小说这个领域大家普遍在用的几套做法：

### 1. 长文/超长上下文是最难的一关，几乎人人都有各自的办法
- **分层注入上下文**：几乎所有"工作台"类项目都采用 **L0 常驻 / L1 编辑器感知 / L2 按需拉取** 的多级上下文策略（AI-Novel-Writer、storyforge 最典型），配上字数预算保护，绝不给 AI 一次性塞进整本小说。
- **自动压缩**：kimi-writer（到 180K 就触发压缩）、denova（独立压缩模块）、OpenFic（自动压缩窗口）、neuro-book 都实现"接近上下文上限时自动总结历史"。这在长篇小说场景几乎是标配。
- **状态文件 / 账本化**：oh-story-claudecode（tracking-state.json + 12KB 状态卡）、denova（多份状态文件）、NovelClaw（16 个记忆账本）把"当前世界状态、角色状态、伏笔、进度"沉淀成结构化文件，写的时候读取、写完后回填，避免让模型从一大坨正文里自己硬猜。

### 2. 从"一次生成"走向"多个角色协作 + 生产流水线"
- **任务分工**：普遍拆出架构/规划/写作/审稿/修复/一致性检查等角色。oh-story-claudecode 用 7 个分工；denova 用 6 个；NovelClaw 用 9 种。
- **生产流水线**：AI-Novel-Writing-Assistant 的"生成→审核→修复→状态回填→下一章"、neuro-book 的"灵感→世界书→工程→剧情→写作→回补"、chinese-novelist-skill 的分阶段流程，都把一个创作拆成能暂停、能恢复、能校验的流水线。
- **去 AI 味 / 质量守门**：这是中文网文项目最看重的差异化能力——`oh-story` 的确定性检查、`neuro-book` 的 360 条 llmlint 规则、`storyforge` 的反 AI 适配器 + 写作风格预设、`AI-Novel-Writing-Assistant` 的写法引擎 + 反 AI 规则。共同思路是：定好"禁词表 / 机械过渡 / 公式化表达"规则库，对成品做脚本级扫描 + AI 语境判断，再决定是阻断还是建议改。

### 3. 记忆/前后一致的三种路线
- **文件系统 + 状态记录**（最轻量、不依赖外部）：oh-story、denova、chinese-novelist-skill。
- **检索 / 向量库**（中型以上项目标配）：OpenFic（LanceDB 检索）、AI-Novel-Writer（LanceDB，降级全文检索）、storyforge（章节记忆检索）、NovelClaw（chromadb）、neuro-book（sqlite-vec）、AI-Novel-Writing-Assistant（Qdrant）。
- **"世界状态引擎"倒推**（最先进，只有 neuro-book）：用时间线 + 切面推算任意时刻的状态，从根本上解决"设定自相矛盾"。

### 4. "借用已有助手" vs "自己搭全套"，是最大的路线分叉
- **技能包路线**（oh-story、chinese-novelist）：借用已装的 Claude Code / Codex / ZCode 的模型和工具能力，几乎零部署、免 key，但受限于宿主、没有独立界面。
- **完整工作台路线**（其余 9 个）：自己建后台 + 网页/桌面界面 + 数据库 + 检索，功能完整、可控，但部署重、要自配 key。

### 5. 接入模型高度统一 → OpenAI 兼容接口
几乎所有项目都用 **OpenAI `/v1` 兼容接口**作为默认接入方式（storyforge、denova、AI-Novel-Writer、NovelClaw 的 deepseek 都这样），再扩展原生 Anthropic/Gemini 接口。这意味着这些项目之间换模型很方便、可互换性很强。
